VLA-HWBench: Where the Time Goes When VLA Models Run on Edge Hardware

VLA-HWBench measures 18 open VLA models on NVIDIA Jetson AGX Thor and AMD Ryzen AI Max+ PRO 395 with a seven-stage call breakdown, analyzing latency effects of compilation, specialized backends, and low-precision optimization. It finds that edge VLA latency is driven more by action-generation method, runtime, and platform than by model size.

Borui Xu, Hongshi Tan, Wenqi Jiang, Bingsheng He, Ming Wu, Jason Zeng, Michael Heinrich, arXiv, 2026

TL;DR

  • VLA-HWBench decomposes the time of a single inference call into seven stages by running 18 open-source VLA models and 19 reference configurations on NVIDIA Jetson AGX Thor and AMD Ryzen AI Max+ PRO 395.
  • The action generation method determines latency more significantly than model size; on Jetson, action generation is the dominant stage in 14 out of 19 configurations.
  • Kernel fusion and 4-bit weights provide the most significant benefits, but these optimizations are only present for two models on Jetson. Even after optimization, denoising steps remain limited by memory bandwidth, while other stages are constrained by software overhead.

Problem Definition

VLA (vision-language-action) models are increasingly deployed on edge devices embedded in robots. In closed-loop robot control, inference latency can impose real-time constraints, yet most VLA papers report only task success rates.

Existing research covers only some of the ways recent VLAs generate actions, divides a single inference call into at most three stages, and often fails to compare inference optimizations for the same model. This paper measures “where the time in a single call is spent” to determine how VLA models, inference software, and edge hardware should be designed.

Core Idea

The core intuition is not to treat end-to-end latency as a single number, but to decompose it into CPU preprocessing, host-to-device copy, GPU vision encoding, prefill, action generation, CPU postprocessing, and residual time. This allows us to verify whether the action generation method, rather than the number of model parameters, determines the per-stage time distribution.

The latency of a single inference call can be expressed as the sum of seven stages:

Tcall=TS0+TS1+TS2+TS3+TS4+TS5+TS6T_{call}=T_{S0}+T_{S1}+T_{S2}+T_{S3}+T_{S4}+T_{S5}+T_{S6}Tcall​=TS0​+TS1​+TS2​+TS3​+TS4​+TS5​+TS6​

Here, TS6T_{S6}TS6​ is defined as the residual latency obtained by subtracting the sum of S0 through S5. We apply this decomposition to 18 open-source VLA models, their respective release software and alternative backends, and two edge platforms to compare the causes of latency.

Methodology

Benchmark Scope

VLA-HWBench measures the following scope:

  • 18 open-source VLA models
  • The software released by each model and alternative backends
  • NVIDIA Jetson AGX Thor
  • AMD Ryzen AI Max+ PRO 395
  • A 7-stage decomposition for a single inference call

Reference configurations are based on the software executed per call, the number of camera views, the chunk size HHH, and the number of actions executed per call HeH_eHe​ in each release’s own LIBERO evaluation. There are 19 reference configurations in total, as some of the 18 models are included with different action generation settings, such as flow and discrete.

Stage Definitions and Measurement

A single inference call is divided into the 7 stages shown in Table 6.

StageWorkUnitMeasured by
S0 Preprocessingresize, normalize, tokenizeCPUtimer
S1 Host-to-devicecopy the inputscopy enginetimer
S2 Vision encodingimages to tokensGPUtimer or kernel trace
S3 Prefilllanguage model, key-value cacheGPUtimer or kernel trace
S4 Action generationdenoising steps or decoded tokensGPUtimer, step sweep or kernel trace
S5 Postprocessingunnormalize, copy backCPUtimer
S6 Residuallatency minus S0-S5CPUderived

The measurement rules are as follows:

  • Stages executed within another stage by the release code are counted within that stage.
  • Stages inside a captured CUDA graph are separated in the manner described in Section 4.4.
  • Since LeRobot executes vision encoding, prefill, and action generation within a single policy call, we time the policy’s own calls:
    • vision encoding: image-embedding call
    • prefill: language-model call that fills the key-value cache
    • action generation: the remainder of the policy call
  • In FastWAM, vision encoding is the VAE encoding of the image, and prefill is the first frame pass of the text encoder and video transformer.
  • In FlashRT’s GR00T N1.7 backbone graph, vision encoding ends at the first RMSNorm of the language model. The VL self-attention after the language model is counted as action generation, consistent with Isaac-GR00T. Each part holds its share in the graph’s kernel time.

Critical Review

Strengths

  • Quantification of inference bottlenecks via 7-stage decomposition — Measures where time is spent on edge devices by dividing a single inference call of a Vision-Language-Action (VLA) model into preprocessing, host-device copy, vision encoding, prefill, action generation, postprocessing, and residual terms (Evidence: Abstract, Table 6).
  • Comparison design by action generation method — Groups models by flow matching, parallel decoding, autoregressive tokens, and reasoning-then-actions, specifying the software, number of camera views, chunk size HHH, and execution horizon HeH_eHe​ for each configuration to enable comparison of latency differences between methods (Evidence: Abstract, Table 4).
  • Provision of cross-platform latency metrics — Organizes median latency (p50p_{50}p50​), p5p_5p5​–p95p_{95}p95​, time per action, and AMD/Jetson ratio for reference configurations on NVIDIA Jetson AGX Thor and AMD Ryzen AI Max+ PRO 395 to show platform differences (Evidence: Part of Table 7; the provided notes do not contain all rows).

Weaknesses & Questions

  • Lack of experimental evidence for core insights in the provided notes — The Abstract claims that kernel fusion and 4-bit weights provide the most significant benefits, and that after optimization, stages processing a small number of tokens on Jetson are limited by memory bandwidth while others are limited by software. However, tables, figures, or ablation values supporting these effects are not present in the provided notes (Evidence: Abstract; no related tables in provided notes).
  • Difficulty judging fairness of baseline comparisons — While comparing software released by each model and alternative backends, the provided notes do not specify which backends were selected, whether the same optimization level was applied to the same model, or how performance/accuracy trade-offs were handled (Evidence: Abstract, Table 4; no backend selection criteria in provided notes).
  • Insufficient statistical evidence — Part of Table 7 includes p50p_{50}p50​ and p5p_5p5​–p95p_{95}p95​, but the number of repeated runs, standard deviation, and statistical significance tests are not present in the provided notes. The Abstract’s claim of an “82× range on Jetson, 157× on AMD” is difficult to verify without the full Table 7 (Evidence: Abstract, Part of Table 7; no repetition/variance/significance info in provided notes).
  • Unclear relationship between model count and configuration count — The Abstract states that 18 open-source VLA models are measured, but Table 4 lists 19 reference configurations. Since one model can be measured with multiple configurations (e.g., MolmoAct2’s flow/discrete/Think), it is unclear whether conclusions are generalized at the model level or the configuration level (Evidence: Abstract, Table 4) (Interpretation).
  • Residual term and CUDA graph separation may affect conclusions — S6 Residual is a derived value obtained by subtracting S0–S5 from total latency, and the method for separating stages inside a captured CUDA graph relies on Section 4.4. However, since the text of Section 4.4 is not in the provided notes, it is difficult to judge how accurately the residual reflects actual bottlenecks (Evidence: Table 6, A.2; no Section 4.4 text in provided notes) (Interpretation).
  • Limited basis for generalization — Measurements are centered on two edge platforms and LIBERO checkpoints. There are no experiments in the provided notes supporting generalization to other robot tasks, larger models, or different power/clock/memory bandwidth environments (Evidence: Abstract, Table 4, Table 5).

Reproducibility

  • While model-specific code repositories and checkpoint names are available, benchmark measurement code, backend versions, GPU/CPU clock/power settings, number of repetitions, and computational costs are not present in the provided notes (Evidence: Table 4, Table 5; no reproducibility section in provided notes).
