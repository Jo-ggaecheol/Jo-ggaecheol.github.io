## 1-1. 에이전트와 환경

강화학습은 한 문장으로 **"해 보고, 점수를 받고, 점수가 높아지는 쪽으로 행동을 고친다"**이다.

- **에이전트(Agent)**: 행동을 정하는 쪽. 우리 경우엔 Core 정책(신경망)
- **환경(Environment)**: 행동을 받아 세상이 어떻게 바뀌는지 돌려주는 쪽. Isaac Lab 안의 손 + 공구 + 물리 엔진

```
 ┌──────────── 관측 o_t, 보상 r_t ────────────┐
 │                                           ▼
환경 (손 + 손잡이 + 버튼)               에이전트 (정책 π)
 ▲                                           │
 └──────────────── 행동 a_t ─────────────────┘
```

| 용어 | 뜻 | 엄지 버튼에서는 |
|---|---|---|
| **상태 s** | 세상의 진짜 전체 정보 | 손·공구·버튼의 정확한 위치·속도·접촉력 전부 |
| **관측 o** | 에이전트가 실제로 볼 수 있는 것 | 관절 각도·속도, 손끝 압력, 모터 전류, 버튼 위치 |
| **행동 a** | 에이전트가 고르는 것 | 관절 목표 변화량 + 손가락별 강성 |
| **보상 r** | 방금 행동이 얼마나 좋았는지 매기는 숫자 하나 | `r_reach + r_press + r_click + …` |

- 시뮬은 공구의 정확한 자세(상태)를 알지만, 실제 V6 손은 압력과 전류(관측)만 안다. 로드맵 카드의 "(교사만) 정확한 물체 자세"가 이 차이다.
- 보상은 여러 항을 더해도 결국 **스칼라 하나**다. 그래서 가중치가 중요하다 (4장).

## 1-2. 에피소드, 리턴, 할인율 γ

**에피소드**: 루프를 시작부터 끝까지 한 번 돈 것 (게임 한 판).

```
reset() → (o₀) → a₀ → (o₁, r₁) → a₁ → (o₂, r₂) → … → 종료
```

| 종료 종류 | 뜻 | 엄지 버튼에서는 |
|---|---|---|
| **terminated** | 성공·실패로 끝남 | 클릭 성공, 공구 떨어뜨림(SLIP) |
| **truncated** | 결과 없이 시간이 다 됨 | TIMEOUT (예: 5초 = 250스텝) |

**리턴**: 에이전트의 목표는 지금 보상이 아니라 **에피소드 끝까지 받을 보상의 합**을 최대로 만드는 것이다.

```
G_t = r_{t+1} + γ·r_{t+2} + γ²·r_{t+3} + …      (0 ≤ γ < 1)
```

엄지를 버튼 쪽으로 옮기는 순간엔 이득이 없어도, 그래야 나중에 `r_press`와 `r_click`(+10)을 받는다. 그 판단 기준이 리턴이다.

**할인율 γ**: 멀리 있는 보상일수록 깎는다. 20스텝 뒤 +10의 현재 가치:

| γ | 현재 가치 | 성격 |
|---|---|---|
| 0.5 | ≈ 0.00001 | 근시안 |
| 0.9 | ≈ 1.2 | 조금 보임 |
| 0.99 | ≈ 8.2 | 거의 그대로 |

- 깎는 이유: 합이 무한대가 되지 않게, 먼 미래는 불확실하니까, 빨리 끝내도록 유도하려고
- **γ가 보는 시야 ≈ 1 / (1 − γ) 스텝**. γ = 0.99면 약 100스텝. 보통 0.99 근처를 쓴다
- 보상을 "접근 → 진행률 → 클릭"처럼 단계형으로 주는 이유도 여기 있다. 클릭 +10만 주면 멀리 있는 보상이 흐릿하게 보이고 우연히 클릭할 일도 거의 없다

## 1-3. MDP (마르코프 결정 과정)

**MDP = (S, A, P, R, γ)**

| 기호 | 이름 | 엄지 버튼에서는 |
|---|---|---|
| S | 상태 공간 | 손·공구·버튼의 모든 위치·속도·접촉 |
| A | 행동 공간 | 관절 목표 변화량 + 강성 (연속값) |
| P | 전이 확률 P(s′ \| s, a) | **물리 엔진** |
| R | 보상 함수 | `r_reach + r_press + r_click …` |
| γ | 할인율 | 0.99 |

- **P는 몰라도 된다.** `step()`으로 결과만 받아 배우는 방식이 model-free RL이고 PPO도 여기 속한다. 우리가 정할 것은 S·A·R·γ와 종료 조건이다. **문제 카드를 짠다 = MDP를 정의한다.**
- **마르코프 성질**: 다음 상태는 현재 상태와 행동만으로 정해진다. 과거는 필요 없다.
- 그런데 **관측만 보면 이 성질이 자주 깨진다** (POMDP). 실제 로봇 문제는 거의 다 POMDP다.

| 관측 | 마르코프인가 |
|---|---|
| 관절 각도만 | ❌ 속도를 몰라 다음 위치를 예측 못 함 |
| 관절 각도 + 속도 | 거의 ✅ |
| + 손끝 압력 | 공구 미끄러짐까지 보면 여전히 부족 |
| + 직전 행동 | 모터 지연이 있을 때 도움 |

해결: 속도·직전 행동을 관측에 넣기, 최근 몇 스텝 쌓기(frame stacking), RNN, 교사–학생(6장).

## 1-4. 정책(Policy)과 가치함수(Value Function)

**정책 π(a | o)**: 관측을 보고 행동을 고르는 규칙.

- 결정적 정책: 같은 관측 → 항상 같은 행동
- 확률적 정책: 연속 행동이면 보통 정규분포

```
신경망(o) → 평균 μ, 표준편차 σ
a ~ Normal(μ, σ)     ← 학습 중 (σ만큼 흔들림 = 탐험)
a = μ                ← 실기 배포
```

**가치함수 V(s)**: 이 상황에서 정책대로 계속하면 받을 리턴의 평균 = **상황 점수**.

**Q함수 Q(s, a)**: 이 **특정 행동 a를 먼저 하고**, 그 뒤로 정책대로 했을 때 리턴의 평균.

**Advantage A(s, a) = Q(s, a) − V(s)**: "이 행동이 여기서 평소 하던 것보다 얼마나 나은가". A > 0이면 그 행동 확률 ↑, A < 0이면 ↓.

**PPO 안의 신경망 두 개**

| 신경망 | 역할 | 입력 | 실기에 가나 |
|---|---|---|---|
| Actor (정책 π) | 행동을 고른다 | 관측 | ✅ |
| Critic (가치함수 V) | 상황을 평가해 Advantage 계산을 돕는다 | 관측 또는 **상태** | ❌ |

> 정책 = 선수, 가치함수 = 코치. 코치는 경기장(실기)에 안 나가니 정답지(상태)를 봐도 된다.

## 1-5. 탐험과 활용

| | 뜻 | 엄지 버튼에서는 |
|---|---|---|
| 활용 | 지금까지 가장 좋았던 행동 | "아래로 누르면 +였지" → 계속 아래로 |
| 탐험 | 안 해 본 행동도 시도 | 옆으로, 다른 각도로, 강성을 바꿔서 |

활용만 하면 버튼 가장자리를 비스듬히 누르는 어설픈 방법에 갇히고, 탐험만 하면 배운 걸 못 써먹는다.

**PPO에서 탐험하는 방법**
1. 확률적 정책의 σ. 학습되면서 저절로 줄어든다
2. 엔트로피 보너스 (σ가 너무 빨리 줄지 않게)
3. 병렬 환경 4096개가 각자 다르게 시도
4. 랜덤 시작 / 도메인 랜덤화

**학습 곡선 신호**: entropy가 너무 빨리 0으로 → 탐험 부족·국소 최적 의심 / 계속 높음 → 확신이 없거나 보상 신호가 약함.

## Q&A

### Q1. 상태와 관측을 왜 나누나? 관측만 넣으면 되지 않나?

**정책에는 관측만 넣는 게 맞다.** 실기에는 관측밖에 없으니까. 그래도 나눠서 생각하는 이유는 세 가지다.

1. **관측이 부족하면 학습 자체가 안 된다.** 각도만 있고 속도가 없으면 엄지가 다가가는 중인지 멀어지는 중인지 모른다 → 부분 관측(POMDP)
2. **보상은 상태로 계산해도 된다.** 보상은 학습 때만 쓰니까. `r_push`(공구가 손 안에서 돈 각도)는 실기로는 못 재지만 시뮬은 안다
3. **학습을 돕는 쪽(critic, 교사)은 상태를 받아도 된다.** 로드맵의 "(교사만)"이 이것

| | 쓰는 정보 | 실기에서도 쓰나 |
|---|---|---|
| 정책 (actor, 학생) | 관측만 | ✅ |
| 보상 계산 | 상태 | ❌ |
| critic, 교사 | 상태 가능 | ❌ |

### Q2. 한 사이클(에피소드)을 예시로 끝까지 정리하면?

설정: 커리큘럼 ①(이미 쥔 상태에서 엄지로 누르기), 정책 50 Hz, 물리 200 Hz(`decimation = 4`), 최대 250스텝.

```
t=0   reset() → 엄지–버튼 2.0 cm → o₀
t=0   정책이 o₀ → a₀ → 물리 4번 (0.02초)
t=1   o₁ (1.8 cm), r₁ = −1.8        → 버퍼에 (o₀, a₀, r₁)
t=2   o₂ (1.5 cm), r₂ = −1.5        → 버퍼에 (o₁, a₁, r₂)
 ⋮
t=40  접촉, 눌림 0.3 mm → r = +0.2
 ⋮
t=55  3 mm 도달 → 클릭! r = +10.2, terminated
```

- 보상은 받는 즉시 합치지 않고 **스텝별로 저장**했다가, 각 스텝의 리턴·advantage를 따로 계산한다
- **정책은 매 스텝 고치지 않는다.**

```
반복:
  ① rollout: 환경 4096개 × 24스텝 ≈ 10만 개 경험 수집 (정책 고정, 끝난 환경은 자동 reset)
  ② 평가: 스텝마다 advantage 계산
  ③ 정책 수정: 좋았던 행동 확률 ↑, 나빴던 행동 ↓
  ④ ①로
```

> 에피소드 하나 ≠ 업데이트 하나. 둘은 따로 도는 단위다.

### Q3. 그러면 보상·critic처럼 실기로 안 나가는 것은 상태값으로 진짜 점수를 내서 평가하는 건가?

맞다. critic에 상태를 주는 방식을 **asymmetric actor-critic**이라고 한다. 단서 두 가지:
- 보상은 "진짜 점수"가 아니라 **"우리가 정한 점수"**다. 보상 식이 틀리면 엉뚱한 걸 잘하게 된다 (4장 보상 해킹)
- 실기 성공 판정은 관측으로 만들어야 한다 → 로드맵 원칙 "시뮬 성공 판정은 실기 판정기와 같은 신호(압력 패턴, 클릭 힘 변화, 전류)로"

### Q4. 아타리처럼 과거 정보를 쌓아서 상태를 추정하는 것과 같은 건가?

같다. DQN(2015) 아타리는 화면 한 장으로 공의 속도를 모르니 **최근 4프레임을 쌓아서**(frame stacking) 넣었다. 로봇 손은 관절 속도를 직접 넣을 수 있어서 이력이 짧아도 되는 경우가 많고, 마찰·질량 같은 숨은 물리값을 추정할 때는 긴 이력 + 학습된 추정기(HORA의 adaptation module)를 쓴다.

### Q5. V는 상황 점수, Q는 이 상황에서 이 정책으로 행동했을 때 평균 점수? Advantage는 무엇을 기준으로 어떻게 평가하나?

- Q는 "정책대로"가 아니라 **"이 행동 하나를 먼저 하고 그다음부터 정책대로"**
- Advantage의 비교는 "지금 vs 나중"이 아니라 **"이 행동 vs 여기서 평소 하던 행동"**

| 상황 | 행동 | Q | V | A |
|---|---|---|---|---|
| 버튼 2 cm 앞 | 버튼 쪽으로 | +7 | +5 | **+2** ↑ |
| 버튼 2 cm 앞 | 반대쪽으로 | +1 | +5 | **−4** ↓ |
| 공구 기울어짐 | 다시 꽉 쥐기 | −1 | −3 | **+2** ↑ (나빠도 평소보다 나음) |

- 평가 대상은 정책 전체가 아니라 **그 스텝의 행동 하나**
- PPO엔 Q 신경망이 없고 critic V로 추정한다:

```
A_t ≈ r_{t+1} + γ·V(s_{t+1}) − V(s_t)
      └── 실제로 해 보니 ──┘   └ 예상 ┘
```

  실제로는 여러 스텝을 섞은 GAE를 쓴다 (3장). critic에 상태를 넣으면 advantage도 정답 정보 기반이 된다.

### Q6. 강화학습 설계자가 직접 정해야(튜닝해야) 하는 곳은?

CartPole 실습 코드에는 없다. 남이 만든 환경을 쓰기만 했고 정책은 무작위였으니까. 설계자가 정하는 값은 **환경 안에** 들어 있다.

| 설계 항목 | CartPole | 엄지 버튼 (로드맵 카드) |
|---|---|---|
| 관측 | 위치·속도·각도·각속도 | 관절, 압력, 전류, 버튼 위치, 직전 행동 |
| 행동 | 좌/우 (이산) | 관절 목표 변화량 + 강성 (연속) |
| **보상** | +1/스텝 | `r_reach`, `r_press`, `r_click` … **가장 많이 튜닝** |
| 종료 | 각도 > 12°, 위치 > ±2.4 | 클릭, SLIP, TIMEOUT |
| 시간 제한 | 500스텝 | 250스텝 |
| 시작 상태 | ±0.05 무작위 | 시작 자세 ±15 mm |
| 물리 | 질량, 길이, 힘 10 N, dt 0.02초 | 마찰, 작동력, 스트로크 + 랜덤화 범위 |

여기에 학습 하이퍼파라미터(γ, learning rate, rollout 길이, entropy 계수)가 더해진다 (2·3장).

### Q7. 규칙 정책 if문은 "단순한 마르코프 분기"인가?

- 현재 관측만 보고 행동 → **마르코프 정책** (memoryless)
- 같은 obs면 항상 같은 행동 → **결정적 정책**
- 기준을 넘으면 확 바꾸는 방식 → 제어 분야의 **bang-bang 제어**

즉 "obs → action 함수"를 사람이 if문으로 짠 것이고, RL은 이 함수를 신경망이 찾게 하는 것이다.

### Q8. AI 시대에 RL에서 사람이 관여할 곳은 k 같은 값을 정하는 것인가? 보상 설계·쉐이핑이 여기에 속하나?

**k는 사람이 정할 값이 아니다.** k는 *정책 안의* 숫자이고, RL이 자동으로 찾는 대상이다. PPO는 이런 숫자 수만 개를 한꺼번에 찾는다.

**보상 설계·쉐이핑은 사람 몫이 맞다.** 다만 k와는 층이 다르다. k는 "어떻게 풀까"이고, 보상은 "무엇을 잘한 걸로 칠까"이다.

| 층 | 예 | 누가 정하나 |
|---|---|---|
| 정책 파라미터 | k, 신경망 가중치 | **RL이 자동으로** |
| 문제 설정 값 | 보상 가중치(−1.0/cm, +10), γ·lr, 랜덤화 범위, 커리큘럼 | 사람 + 자동 탐색 (sweep, Eureka, LLM) |
| 목표와 판단 | 무엇이 성공인가, 하면 안 되는 것(과한 힘·공구 파손), 실기에서 정말 되는가 | **사람** |

AI 시대에 바뀐 것과 안 바뀐 것:
- **LLM이 잘하는 것**: env·보상 코드 작성, 학습 결과를 보고 보상을 고쳐 다시 돌리는 반복 (Eureka가 29개 과제 중 83%에서 사람 보상보다 나았다)
- **사람이 여전히 해야 하는 것**
  - **목표 정의**: "클릭"이 무엇이고 몇 N까지 눌러도 되는지. 공구·공정·고객 요구에서 온다
  - **행동을 보고 판단**: 보상 곡선은 올랐는데 영상을 보면 버튼을 옆에서 문지르고 있다 → 보상 해킹을 알아채는 눈
  - **하드웨어와 안전**: V6 손끝 17.3 N, 연속 작업 발열, MCU 하드 한계
  - **실기 검증**: 시뮬에서 된 것이 V6에서 되는지, 안 되면 시뮬의 무엇이 틀렸는지

> 사람의 일은 "숫자를 맞추는 것"에서 **"무엇을 잘해야 하는지 정하고, 정말 잘하는지 확인하는 것"**으로 옮겨 가고 있다.

### CartPole

카트 위에 막대를 세워 두고, 카트를 좌우로 밀어 막대가 안 넘어지게 버티는 문제.

| | 내용 |
|---|---|
| 관측 `obs` | `[카트 위치(m), 카트 속도(m/s), 막대 각도(rad), 막대 각속도(rad/s)]`, 각도 + = 오른쪽으로 기울어짐 |
| 행동 | `0` 왼쪽, `1` 오른쪽 |
| 보상 | 버틴 스텝마다 +1 → 리턴 = 버틴 스텝 수 |
| terminated | 각도 > 12° 또는 위치 > ±2.4 |
| truncated | 500스텝 (사실상 성공) |

### 코드 1: 루프 (`code/ch01/cartpole_loop.py`)

```python
import gymnasium as gym

env = gym.make("CartPole-v1")

for episode in range(3):
    obs, info = env.reset(seed=episode)   # 에피소드 시작, 첫 관측 o₀
    episode_return = 0.0
    t = 0

    while True:
        action = env.action_space.sample()   # 정책 자리. 지금은 무작위
        next_obs, reward, terminated, truncated, info = env.step(action)   # RL 루프의 심장

        episode_return += reward
        obs = next_obs        # 빼먹으면 정책이 계속 옛날 관측만 봄
        t += 1

        if terminated or truncated:
            print(f"[에피소드 {episode}] 길이 {t}스텝, 리턴 {episode_return:.0f}")
            break

env.close()
```

실행 결과:

```
t=  0  o=[ 0.014 -0.023 -0.046 -0.048]  a=0  r=1.0  terminated=False  truncated=False
t=  1  o=[ 0.013 -0.217 -0.047  0.23 ]  a=1  r=1.0  terminated=False  truncated=False
...
[에피소드 0] 길이 17스텝, 리턴 17, 종료: terminated
[에피소드 1] 길이 17스텝, 리턴 17, 종료: terminated
[에피소드 2] 길이 37스텝, 리턴 37, 종료: terminated
```

t=0에서 왼쪽으로 밀자 카트 속도가 −0.023 → −0.217, 반작용으로 막대 각속도가 −0.048 → +0.23 (오른쪽으로 넘어가기 시작).

### 코드 2: 규칙 정책 비교 + 할인 리턴 (`code/ch01/rule_policies.py`)

무작위 대신 obs를 보고 행동을 정하는 **사람이 짠 정책**. 손바닥 위 빗자루처럼, 기우는 쪽으로 카트를 민다.

```python
policies = {
    "무작위":              None,
    "각도만 obs[2]":        lambda o: o[2] > 0,
    "각속도만 obs[3]":      lambda o: o[3] > 0,
    "각도 + 1.0 × 각속도":  lambda o: o[2] + 1.0 * o[3] > 0,
    "각도 + 0.5 × 각속도":  lambda o: o[2] + 0.5 * o[3] > 0,
    "각도 + 0.1 × 각속도":  lambda o: o[2] + 0.1 * o[3] > 0,
}
...
G += reward                      # 할인 없는 리턴
G_disc += (GAMMA ** t) * reward  # γ = 0.99 할인 리턴
```

결과 (seed 0~19, 20 에피소드):

| 정책 | 평균 리턴 | 최소 | 최대 | 평균 할인 리턴 (γ=0.99) |
|---|---|---|---|---|
| 무작위 | 22.1 | 11 | 39 | 19.7 |
| 각도만 | 40.9 | 25 | 52 | 33.5 |
| 각속도만 | 198.7 | 138 | 278 | 85.5 |
| 각도 + 1.0 × 각속도 | 491.7 | 334 | 500 | 99.2 |
| 각도 + 0.5 × 각속도 | **500.0** | 500 | 500 | 99.3 |
| 각도 + 0.1 × 각속도 | **500.0** | 500 | 500 | 99.3 |

### 무엇을 확인했나

1. **정책 = obs → action 함수.** obs를 쓰기 시작하자 무작위보다 2배 버틴다
2. **속도가 왜 필요한가 (1-3).** 각도만 보면 이미 기운 뒤에 반응해 흔들림이 커진다 (40.9). 각속도를 보면 넘어가는 *중*에 미리 반응한다 (198.7). 둘 다 보면 500. 각도만 쓰는 정책은 **속도를 못 보는 부분 관측**과 같다
3. **k를 손으로 바꾸는 게 튜닝.** k = 0.5, 0.1에서 매번 500. PPO는 이런 숫자 수만 개를 자동으로 찾는다 (2장에서 같은 문제를 신경망으로)
4. **γ의 시야 (1-2).** 500스텝을 버텨도 할인 리턴은 99.3에서 멈춘다. (1 − 0.99⁵⁰⁰) / (1 − 0.99) ≈ 99.3. γ = 0.99는 대략 100스텝 앞까지만 본다는 뜻이다
