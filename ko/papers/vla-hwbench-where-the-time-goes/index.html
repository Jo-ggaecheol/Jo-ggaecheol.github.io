VLA-HWBench: Where the Time Goes When VLA Models Run on Edge Hardware

VLA-HWBench는 18개 오픈 VLA 모델을 NVIDIA Jetson AGX Thor와 AMD Ryzen AI Max+ PRO 395에서 7단계 호출 분해로 측정하고, 컴파일·전문 백엔드·저정밀화 최적화의 지연 효과를 분석한다. 결과적으로 엣지 VLA 지연은 모델 크기보다 액션 생성 방식과 런타임·플랫폼에 따라 달라진다.

TL;DR

  • VLA-HWBench는 공개 VLA 모델 18개와 19개 참조 구성을 NVIDIA Jetson AGX Thor, AMD Ryzen AI Max+ PRO 395에서 실행해 한 inference call의 시간을 7단계로 분해한다.
  • 액션 생성 방식이 모델 크기보다 지연을 더 크게 결정하며, Jetson에서는 19개 구성 중 14개에서 action generation이 가장 큰 단계다.
  • kernel fusion과 4-bit weights가 가장 큰 도움을 주지만 두 모델·Jetson에서만 존재하고, 이후에도 denoising steps는 memory bandwidth, 나머지 단계는 software overhead로 제한된다.

문제 정의

VLA(vision-language-action) 모델은 점점 로봇에 탑재된 edge device에서 실행된다. 폐쇄 루프 로봇 제어(closed-loop robot control)에서는 추론 지연(latency)이 실시간 제약을 만들 수 있지만, 대부분의 VLA 논문은 task success만 보고한다.

기존 연구는 최근 VLA가 액션을 생성하는 방식 중 일부만 다루고, 한 inference call을 최대 3단계로만 나누며, 같은 모델에서 추론 최적화를 비교하지 않는 경우가 많다. 이 논문은 VLA 모델, 추론 소프트웨어, edge hardware를 어떻게 설계해야 하는지 판단하기 위해 “한 호출의 시간이 어디에 쓰이는가”를 측정한다.

핵심 아이디어

핵심 직관은 end-to-end latency를 단일 숫자로 두지 않고, CPU 전처리, host-to-device copy, GPU vision encoding, prefill, action generation, CPU 후처리, 잔여 시간으로 나누어 보는 것이다. 이렇게 하면 모델 파라미터 수가 아니라 액션 생성 방식이 stage별 시간 분포를 결정하는지 확인할 수 있다.

한 inference call의 지연을 7단계 합으로 표현하면 다음과 같다.

Tcall=TS0+TS1+TS2+TS3+TS4+TS5+TS6T_{call}=T_{S0}+T_{S1}+T_{S2}+T_{S3}+T_{S4}+T_{S5}+T_{S6}Tcall​=TS0​+TS1​+TS2​+TS3​+TS4​+TS5​+TS6​

여기서 TS6T_{S6}TS6​은 S0부터 S5까지의 합에서 뺀 residual latency로 정의된다. 이 분해를 18개 공개 VLA 모델, 각 release 소프트웨어와 대체 백엔드, 두 edge 플랫폼에 적용해 지연의 원인을 비교한다.

방법론

벤치마크 범위

VLA-HWBench는 다음 범위를 측정한다.

  • 공개 VLA 모델 18개
  • 각 모델이 공개한 software와 alternative backends
  • NVIDIA Jetson AGX Thor
  • AMD Ryzen AI Max+ PRO 395
  • 한 inference call에 대한 7단계 분해

참조 구성은 각 release의 자체 LIBERO evaluation이 한 call마다 실행하는 software, camera views 수, chunk size HHH, 그리고 call당 실행 동작 수 HeH_eHe​를 기준으로 한다. 전체 참조 구성은 19개이며, 이는 모델 18개 중 일부가 flow와 discrete 등 서로 다른 action generation 설정으로 포함되기 때문이다.

단계 정의와 측정

한 inference call은 Table 6의 7단계로 나뉜다.

StageWorkUnitMeasured by
S0 Preprocessingresize, normalize, tokenizeCPUtimer
S1 Host-to-devicecopy the inputscopy enginetimer
S2 Vision encodingimages to tokensGPUtimer or kernel trace
S3 Prefilllanguage model, key-value cacheGPUtimer or kernel trace
S4 Action generationdenoising steps or decoded tokensGPUtimer, step sweep or kernel trace
S5 Postprocessingunnormalize, copy backCPUtimer
S6 Residuallatency minus S0-S5CPUderived

측정 규칙은 다음과 같다.

  • release code가 다른 stage 안에서 실행하는 stage는 그 안에 count된다.
  • captured CUDA graph 내부의 stage는 Section 4.4에서 설명하는 방식으로 분리한다.
  • LeRobot은 vision encoding, prefill, action generation을 policy call 하나 안에서 실행하므로, policy의 own calls를 time한다.
    • vision encoding: image-embedding call
    • prefill: key-value cache를 채우는 language-model call
    • action generation: policy call의 나머지
  • FastWAM에서는 vision encoding이 image의 VAE encoding이고, prefill은 text encoder와 video transformer의 first frame pass다.
  • FlashRT의 GR00T N1.7 backbone graph에서는 vision encoding이 language model의 first RMSNorm에서 끝난다. language model 이후의 VL self-attention은 action generation으로 count되며, 이는 Isaac-GR00T와 같다. 각 부분은 graph의 kernel time에서 그 share를 가진다.

핵심 insight 중 하나는 kernel fusion과 4-bit weights가 가장 큰 도움을 준다는 것이다. 그러나 제공된 메모에 따르면 이 최적화는 두 모델에서만, Jetson에서만 존재한다.

핵심 수치는 다음과 같다.

  • Jetson에서 reference configuration 간 지연은 82×82\times82× 범위까지 벌어진다.
  • AMD 플랫폼에서는 157×157\times157× 범위까지 벌어진다.

  • time per action은 latency를 chunk size HHH로 나눈 값이다.
  • 50 ms 초과 값은 해당 configuration이 LIBERO가 실행하는 속도보다 느리게 actions를 생성함을 의미한다.

최적화 실험에서는 π0.5\pi_{0.5}π0.5​와 GR00T N1.7에 대해 단계별 최적화를 적용하고, fastest configuration의 누적 latency와 stage speed-up을 Figure 5에서 보고한다. 제공된 메모에는 구체적인 speed-up 수치 표가 별도로 포함되어 있지 않다.

최적화 이후 bottleneck 분석에서는 Jetson에서 소수 토큰을 처리하는 stage, 특히 denoising steps가 memory bandwidth로 제한되고, 나머지 stage는 software로 제한된다고 보고한다. 이 결과는 Figure 9와 Figure 10의 roofline 및 kernel class 분해와 연결된다.

비판적 검토

강점

  • 7단계 분해로 추론 병목 정량화 — 비전-언어-액션(VLA, vision-language-action) 모델의 한 추론 호출(inference call)을 전처리, 호스트-디바이스 복사, 비전 인코딩(vision encoding), 프리필(prefill), 액션 생성(action generation), 후처리, 잔여항으로 나누어 엣지 디바이스(edge device)에서 시간이 어디에 쓰이는지를 측정한다 (근거: Abstract, Table 6).
  • 액션 생성 방식별 비교 설계 — flow matching, parallel decoding, autoregressive tokens, reasoning-then-actions로 모델을 묶고 각 구성의 소프트웨어, 카메라 뷰 수, 청크 크기 HHH, 실행 지평 HeH_eHe​를 명시하여 방식 간 지연 차이를 비교할 수 있게 한다 (근거: Abstract, Table 4).
  • 플랫폼 간 지연 지표 제공 — reference configuration에 대해 Jetson AGX Thor와 AMD Ryzen AI Max+ PRO 395의 median latency(p50p_{50}p50​), p5p_5p5​–p95p_{95}p95​, action당 시간, AMD/Jetson 비율을 정리해 플랫폼 차이를 보여준다 (근거: Table 7 일부; 제공된 메모에는 전체 행이 없다).

약점·의문

  • 핵심 insight의 실험 근거가 제공된 메모에 부족하다 — Abstract은 커널 퓨전(kernel fusion)과 4-bit 가중치가 가장 큰 도움을 주며, 최적화 후에도 Jetson에서 소수 토큰 처리 단계는 메모리 대역폭(memory bandwidth)으로 제한되고 나머지는 소프트웨어로 제한된다고 주장하지만, 해당 효과를 뒷받침하는 표·그림·ablation 수치가 제공된 메모에 없다 (근거: Abstract; 제공된 메모에 관련 표 없음).
  • baseline 비교의 공정성 판단이 어렵다 — 각 모델이 공개한 소프트웨어와 대체 백엔드(alternative backends)를 비교한다고 하나, 어떤 백엔드를 선택했는지, 동일 모델에서 동일한 최적화 수준으로 맞췄는지, 성능/정확도 trade-off를 어떻게 처리했는지가 제공된 메모에 없다 (근거: Abstract, Table 4; 제공된 메모에 backend 선택 기준 없음).
  • 통계적 근거가 불충분하다 — Table 7 일부에는 p50p_{50}p50​과 p5p_5p5​–p95p_{95}p95​가 있으나 반복 실행 횟수, 표준편차, 통계적 유의성 검정은 제공된 메모에 없다. Abstract의 “Jetson에서 82×, AMD에서 157× 범위” 주장도 전체 Table 7이 없어 확인하기 어렵다 (근거: Abstract, Table 7 일부; 제공된 메모에 반복/분산/유의성 정보 없음).
  • 모델 수와 구성 수의 관계가 명확하지 않다 — Abstract은 18개 공개 VLA 모델을 측정한다고 하지만 Table 4는 19개 reference configuration을 나열한다. MolmoAct2의 flow/discrete/Think처럼 한 모델이 여러 구성으로 측정될 수 있어, 결론을 모델 단위인지 구성 단위인지로 일반화하는지 불명확하다 (근거: Abstract, Table 4)(해석).
  • 잔여항과 CUDA graph 분리가 결론에 영향을 줄 수 있다 — S6 Residual은 전체 latency에서 S0–S5를 뺀 유도값이고, captured CUDA graph 내부 stage 분리 방법은 Section 4.4에 의존한다. 그러나 제공된 메모에는 Section 4.4 본문이 없어 residual이 실제 병목을 얼마나 정확히 반영하는지 판단하기 어렵다 (근거: Table 6, A.2; 제공된 메모에 Section 4.4 본문 없음)(해석).
  • 일반화 근거가 제한적이다 — 측정은 두 엣지 플랫폼과 LIBERO checkpoint 중심이다. 다른 로봇 작업, 더 큰 모델, 다른 전력/클럭/메모리 대역폭 환경으로의 일반화를 뒷받침하는 실험이 제공된 메모에 없다 (근거: Abstract, Table 4, Table 5).

재현 가능성

  • 모델별 코드 저장소와 checkpoint 이름은 있으나 벤치마크 측정 코드, 백엔드 버전, GPU/CPU 클럭·전원 설정, 반복 횟수, 계산 비용이 제공된 메모에 없다 (근거: Table 4, Table 5; 제공된 메모에 재현성 섹션 없음).
